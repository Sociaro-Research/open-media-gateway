# First public release checklist

Publishing the repository is a separate owner decision. Complete these checks
while the repository is private before changing its visibility to public.

## 1. Publication rights

- [ ] Confirm that the code, text, images and product names can be published.
- [ ] Confirm that employee and contractor agreements assign the necessary rights
  to the project owner.
- [ ] Confirm the Apache License 2.0 choice; consult legal counsel if needed.
- [ ] Check the right to use the `Sociaro` / `Media Gateway` name and logo.
- [ ] Exclude internal specifications, roadmaps, exported Google Docs/Slides and
  working research directories unless explicitly approved for publication.
- [ ] Record the source and explicit redistribution permission for every added
  logo, font, screenshot or other asset. Review the embedded provider icons under
  `plugins/provider/*/icon.*` and `web/public/ui/google-icon.svg`; presence in the
  source tree does not establish redistribution or trademark permission.
- [ ] Review redistribution terms and source attribution for recorded vendor
  documentation and pricing fixtures under `internal/providers/testdata/`.

## 2. Secrets and data

- [ ] Review the files before pushing: `git status --short`.
- [ ] Confirm that `.env`, `data/`, `bridge/`, `slides-build/`, `trusted-read-*`,
  local PDF/PPTX/DOCX files and machine-specific plist files are ignored.
- [ ] Scan both tracked files and all reachable Git refs with a tool such as
  Gitleaks; record the exact SHA, scanner version, configuration and limits.
- [ ] Review historical internal documents, machine paths, infrastructure targets
  and author/committer identities. Removing a file from the current tree does
  not remove it from history.
- [ ] Separately review GitHub issues, pull requests, comments, Actions logs and
  artifacts, releases/assets and the wiki for private data. Changing visibility
  can expose Actions history/logs and names of internal reusable workflows.
- [ ] Revoke any key previously included in a commit, log, issue, screenshot or
  shared document. Deleting its file is insufficient.
- [ ] Check fixtures, migrations, UI images and API examples for personal data,
  real prompts, result URLs and account identifiers.

## 3. Private repository preparation

- [ ] If creating a new repository, create it empty and private, without an
  autogenerated README, `.gitignore` or LICENSE, to avoid conflicts.
- [ ] Confirm that the Go module path and imports use the canonical repository
  address, rather than a temporary path such as `media-gateway`.
- [ ] Confirm that the intended source history has been pushed to the private
  repository.
- [ ] Check repository links in release notes, package metadata and images.
- [ ] Add a short GitHub description and topics such as `go`, `generative-ai`,
  `media-generation`, `gateway`, `alibaba-cloud` and `byteplus`.

## 4. GitHub settings before public access

- [ ] Enable private vulnerability reporting.
- [ ] Enable Dependabot alerts/updates, secret scanning and push protection where
  available for the repository type.
- [ ] Create a ruleset for `main` requiring pull requests, successful `Go checks`
  and an up-to-date branch where an approved check integration exists; prohibit
  force pushes and deletion. Do not require an unavailable hosted check.
- [ ] Review fork/PR workflow permissions, secrets and environments before enabling
  hosted execution. Do not run untrusted contributor code with deployment access.
- [ ] Require at least one review once a second maintainer is available.
- [ ] Enable Discussions if a user-question channel is needed.
- [ ] Confirm that the published conduct/security email is monitored and that
  the documented private reporting channels are available.
- [ ] Add `CODEOWNERS` once the GitHub users or teams with write access are known.

## 5. Release candidate verification

- [ ] Clone the private repository on a clean machine.
- [ ] Build the development stack using the README's development instructions.
- [ ] Independently install the matching release bundle using its Quick start;
  check local/server startup and first-owner setup.
- [ ] Create free mock tasks for all four media types and download their results.
- [ ] Run the required checks for the exact release source using the approved
  local workflow, and record executed, skipped and unexecuted checks. Hosted
  Actions are optional and require a separate operator decision.
- [ ] Check README links, OpenAPI, issue forms and the PR template on GitHub.
- [ ] Confirm that the application and UI images include the project license
  and notice, preserve third-party notices, and run as non-root.
- [ ] Include the complete third-party license bundle in the published image.
  Check the older `byteplus-sdk-golang` dependency separately: upstream declares
  Apache-2.0, but the `v1.0.16` module archive omits its LICENSE file.
- [ ] Confirm that repository documentation and interface text are in English,
  with `README.md` as the canonical entry point.

## 6. Publication

- [ ] Choose a version (`v0.1.0` is suitable for a preview) and update `CHANGELOG.md`.
- [ ] Create a signed annotated tag and GitHub Release describing known
  limitations, migrations and verified startup instructions.
- [ ] Change visibility to public only after reviewing the repository contents
  and history again.
- [ ] After publication, recheck the Security tab, license, community profile,
  anonymous cloning and first startup.

## Release automation

The repository has a version-tagged [GHCR release workflow](ghcr-release.md)
for ready-made AMD64/ARM64 installation images and bundles. It preserves private
repository/package access; public access remains an explicit owner decision.
Runtime Go dependency notices are included in the application image, including
the documented upstream fallback for the BytePlus v1.0.16 archive.

`CODEOWNERS` still requires actual GitHub users or teams with write access.
