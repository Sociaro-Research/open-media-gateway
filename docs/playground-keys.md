# Account-managed Playground keys

Sign in, select Profile or a company, then choose **Create Playground key** in
Playground or Templates. This explicit action creates an ordinary generation-only
API key named **Playground & Templates**. Visiting a page or signing in never
creates a credential. Both sections use the same key.

The key list identifies **Created by Playground · Templates** from immutable
`purpose: playground_templates` metadata, independently of the key's name. Normal
keys remain hash-only. Pasting an existing key never saves it into the account vault.

Only an explicitly created Playground key additionally has its secret encrypted
in the account's vault for that workspace. After signing in on another browser,
the same key is restored automatically. Companies and Profile keep separate keys;
other people, including company managers viewing key metadata, cannot restore
your secret. Existing key-issuance permissions still apply when creating a key.

The authenticated owner receives the secret in a no-store response and the
browser keeps it in its existing session-scoped key module. **The secret is
therefore accessible to the authenticated browser and its JavaScript.** Use HTTPS
outside loopback development. This is encrypted account storage, not a server-only
proxy: normal generation API requests still use `Authorization: Bearer` and omit
the sign-in cookie. Login sessions do not authorize generation by themselves.

**Forget key** clears this tab and pauses automatic restoration there until
**Use saved key** or another sign-in. Signing out clears local credentials without
deleting the account association. A pasted manual key retains the existing
24-hour tab policy. Neither action revokes a key. Revoke in **Manage keys** to stop
future use; expiry and membership/account restrictions apply to restored keys too.
Inactive keys are never automatically replaced. Create again explicitly after
revocation/expiry, subject to current permissions. Previously accepted jobs retain
the existing execution, history, billing and media-access rules.

`POST /v1/playground-key/create` requires an authenticated owner's session and a
stable UUID `request_id`. Retry that ID after an uncertain response; concurrent
creates converge on the current key. Replaying a revoked/expired creation fails;
replaying a superseded request returns a conflict. A fresh explicit action can
replace an inactive key. `POST /v1/playground-key/restore` retrieves only the
owner's saved key for the supplied company, or Profile when omitted. Neither
endpoint accepts bearer credentials as authority to retrieve a secret. See
[OpenAPI](openapi.yaml) for the request and response contracts.

At rest, the vault uses AES-GCM with a random nonce, a separate encryption domain
derived from the existing `PROVIDER_CREDENTIALS_KEY`, and authenticated binding
to purpose, account, workspace and key ID. Ordinary API authentication still
looks up the normal key hash and checks current policy. Preserve and protect the
operator-managed encryption secret with backups; changing/losing it does not
recover old vault contents. Decryption failure stops restore without creating a
replacement. Recovery requires restoring the correct encryption secret or
revoking the old key and explicitly creating another one. No production master
key is generated by this feature.
